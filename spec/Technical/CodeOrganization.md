# 代码组织与职责边界

本页规定 Subvaults 的代码组织方式，以项目 [AGENTS.md](../../AGENTS.md) 为准，并借鉴 ECMenu 按业务能力组织、明确状态所有权及集中装配依赖的做法。产品行为与验收边界见[需求总览](../Requirements/Main.md)。

本页记录编码约定与能力边界。实际源码入口由[技术导航](Main.md)定位，数据所有权和存储完成点集中在[数据与提交](PluginData.md)。

## 按能力组织

代码从业务能力进入，再按实际复杂度划分职责。能力边界如下：

| 能力或入口 | 职责 |
| --- | --- |
| Subvaults | 文件夹绑定与唯一性、创建、外观管理、移除、文件夹生命周期，以及对应的创建和管理交互 |
| FileNavigation | 当前视图切换、内部内容与外部打开文件的显示规则、导航内新建、状态恢复，以及标题和切换条的呈现 |
| 插件入口与装配 | 构造能力实例、连接生产适配器，管理加载、事件订阅与卸载 |

同一能力的规则、操作与界面保持可共同定位。简单能力使用少量职责清楚的文件；形成独立维护责任时，再建立能力内部的职责目录。目录随实现建立。

不同责任分文件表达，同一责任中的紧密相关类型可以放在一起。文件拆分依据独立职责和共同变化关系；每份源码文件用简洁的中文文档注释说明职责与关键边界。

## 职责与依赖方向

| 职责 | 输入与输出 | 在本插件中的应用 |
| --- | --- | --- |
| Domain | 不可变事实 → 类型化决定、计划或预期失败 | 路径归属、重复绑定判断、文件夹变更后的配置更新、内外文件归属 |
| Application | 类型化意图 → 读取事实、计算规则、执行操作并发布结果 | 创建 subvault、处理文件夹生命周期、切换视图、协调导航内新建 |
| Persistence | 保存或恢复请求 → 存储结果或明确失败 | 插件配置与导航恢复数据的编码、读取和保存 |
| Platform | 能力所需的窄请求 → 宿主事实、操作结果或接入失败 | Obsidian vault 与工作区事件、原生文件导航接入、真实文件创建 |
| Presentation | 业务状态与用户事件 → 控件显示、交互草稿及应用操作请求 | 创建面板、选择列表、标题、切换条、右键菜单和操作反馈 |

这五类表达责任，能力内部按需采用。纯规则与副作用实现始终分属不同文件和模块。

呈现向应用操作提交意图；应用操作调用纯规则及窄的存储、宿主接口；生产适配器由插件入口集中连接。接口靠近使用它的能力定义，按实际调用与替换需要选择函数或接口。

纯规则不依赖 Obsidian 界面对象、DOM、文件系统、时钟或随机数。身份生成等副作用由外部执行，生成结果作为规则的输入。插件入口与开发诊断入口调用相同业务能力，命令行解析和进程退出由入口处理。

## 领域类型与状态所有权

使用领域类型表达 subvault 身份、工作文件夹路径、图标和预设色等有效值，以可辨识联合表达当前选择、交互阶段及预期失败。外部输入在进入业务边界时验证，内部规则使用已经建立约束的值。

每份可变状态有一个明确的所有者。其他模块通过只读状态或已完成操作的结果协作；缓存和界面投影需注明来源与失效条件。具体状态与生命周期见[状态所有权](PluginData.md#状态所有权)。

## 存储与操作完成点

业务模型与存储编码结构分别按语义和存储责任组织。共享文档的保存由统一边界协调，操作结果明确表达实际已经完成的业务效果。具体存储流程和完成点见[数据与提交](PluginData.md)。

预期失败由类型化结果传递到呈现边界，再转换为英文反馈。内部实现不变量被破坏时明确暴露错误。尚未发布的开发实现按当前模型维护，数据格式迁移在存在实际已发布数据时单独设计。

## 宿主适配与验证

Obsidian 原生控件和公开 API 是界面与宿主接入的优先选择。必须涉及文件导航内部机制的实现集中在明确的适配文件中，记录输入、输出、资源生命周期、失败行为及适用版本。

验证分为纯规则、应用操作和宿主集成三个范围：规则检查有效状态与计算结果，应用检查副作用次序及完成点，集成检查实际文件导航、新建位置、卸载清理和显示稳定性。插件变更通过检查后，构建同步到 `TestVaults/Debug-Vault/` 并重新加载验证。

每个已实现能力的技术文档记录职责、主要执行流、关键源码和失败行为；数据所有权与公共平台结论引用其唯一维护位置。官方接口约定、参考源码观察和项目实测分别标明证据范围。
